# Screenshot and task review

Choose read-only review, polish, redesign or exploration. A review produces findings; it does not authorize implementation or a new visual direction. Judge existing interfaces against their actual system.

Separate visual evidence (hierarchy, spacing, typography, contrast, content fit, responsive composition) from task evidence. For a task, identify the concrete goal and exercise relevant steps/states when runtime access is available and authorized. Record input, action, resulting state and completion/blocker. Screenshots cannot prove completion, validation, keyboard behavior or motion quality.

Give critics the brief, constraints, reference and current captures with viewport/state labels. Omit builder defenses, prior scores and desired verdicts. Use independent critics only when authorized/supported; otherwise call it sequential self-review. Capture states proportional to scope.

Each finding: location/state | observation | evidence | consequence | correction or next check. Separate measurements from judgment; preserve successful details. Hold content and conditions constant when comparing concepts; compare structural differences, not recolorings. For a new screen establish its subject and primary action before polish.

Handoff visual checks and task checks separately. Never claim a flow was tested because screenshots look complete.
